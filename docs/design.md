# 국내주식 매매 제안 브리핑 서비스 설계서

- 문서 상태: 초안
- 대상 저장소: `bluehawhy/stock-briefing`
- 구현 언어: Python
- 운영 환경: 집의 Ubuntu 서버 + Docker
- 실행 주기: 매일 오전 8시 30분 (Asia/Seoul)

## 1. 목표와 범위

국내 주식의 전 거래일 데이터와 추적 대상으로 선택한 계좌의 보유 수량을 바탕으로 종목별 매수·매도·관망 의견과 제안 수량을 계산하고, 매일 오전 8시 30분 카카오톡으로 요약을 전달한다. 한국투자증권과 미래에셋증권을 교체 가능한 provider adapter로 지원한다. 카카오톡을 초기 메시지 채널로 사용한다. 카카오 연동 어댑터는 메시지 송수신과 공통 형식 변환만 맡고, 명령 해석·권한 검사·증권사 연결·계좌와 관심종목 관리·제안·주문·응답 구성은 채널 독립적인 서비스에서 수행한다. 사용자는 일반 텍스트 메시지로 모든 기능을 요청하고 텍스트로 결과를 받는다. 카카오 고유 메뉴·버튼·블록에 업무 기능을 묶지 않는다. 향후 메신저 추가는 송수신 어댑터와 사용자 식별자 연결만 확장한다. 사용자용 대시보드는 초기 범위에 포함하지 않는다. API 키 등록은 메시지로 시작해 공통 보안 등록 화면에서 처리한다.

### 1차 버전에서 할 일

- 모든 사용자 기능을 일반 텍스트 메시지 명령으로 사용할 수 있는 구조 (별도 사용자용 대시보드 없음)
- 한국투자증권·미래에셋증권 API를 provider adapter로 연결할 수 있는 구조
- 국내 주식 시세, 일봉, 거래량, 기관·외국인 수급 데이터 조회
- 메시지에서 연결을 시작하고 보안 등록 화면에서 증권사 API 인증정보 저장·검증
- 계좌 목록 조회 후 추적 계좌를 사용자가 선택하고 추가·제거
- 이동평균선 교차, 52주 가격 범위, 거래량, 투자자별 순매수 조건 계산
- 보유량과 설정된 예산 한도를 고려한 매매 제안 수량 산정
- 제안 근거를 포함한 카카오톡 브리핑 발송
- 공통 메시지 명령을 통한 브리핑·보유량·관심종목·계좌·주문·설정 조회와 변경
- 카카오 메시지 송수신 어댑터가 수신 내용을 공통 입력 형식으로 바꾸고, 독립된 서비스가 DB/API 작업을 수행해 공통 응답을 생성
- 주문 요청 시 주문 요약과 일회용 확인 코드를 텍스트로 보여주고 확인 메시지를 받는 대화 흐름
- 실행 결과, 데이터 기준일·누락 상태, 추천 결과, 발송 상태 기록
- 챗봇 연동 상태 화면: 증권사 연결·토큰 만료, 추적 계좌, 마지막 완전 데이터 기준일, 최근 브리핑 성공 여부
- 제안 기록과 사후 가격 비교를 통한 모의 운용 성과 조회(적중률·가상 손익, 수수료·세금·슬리피지 반영)
- 주문 기능 활성화 시 계좌·종목별/일별 금액 한도, 가격 이탈 검사, 확인 만료, 당일 주문 중지
- 상시 대기하는 메시지 수신 API 컨테이너와 매일 한 번 실행되는 Docker 작업 컨테이너 운영

### 1차 버전에서 제외할 일

- 일회용 확인 메시지를 받지 않은 주문의 자동 제출
- 여러 사용자를 위한 서비스 (단일 사용자 내 여러 증권사·추적 계좌는 지원)
- 별도 사용자용 웹 대시보드
- 실시간 시세 감시, 모델 학습 기반 예측

실제 주문 제출은 1차 기본 설정에서 비활성화한다. 선택한 증권사 API의 주문 기능·계좌 설정을 확인하고, 명시적으로 활성화한 뒤에도 주문 요약과 일회용 확인 메시지를 거쳐야 제출한다. 제안 생성만으로 주문하지 않는다.

## 2. 제안 흐름

```text
Ubuntu systemd timer (매일 08:30 KST)
        |
        v
Docker Compose one-shot 실행
        |
        v
설정·최근 실행 확인
        |
        v
시장 데이터 + 보유량 조회
        |
        v
데이터 최신성·정합성 검사
        |
        v
지표 계산 -> 규칙 평가 -> 수량 산정
        |
        v
브리핑 생성 -> 메시지 발신 어댑터 -> 카카오톡 발송
        |
        v
SQLite 실행 기록·발송 결과 저장
```

### 단계별 동작

1. 서버의 systemd timer가 매일 08:30에 Docker Compose 작업 컨테이너를 실행한다.
2. SQLite에서 종목별 일봉·수급 데이터의 저장 범위와 마지막 완전 수집 거래일을 확인한다.
3. 아직 없는 거래일 데이터만 데이터 공급자 어댑터로 요청한다. 최초 실행 때만 지표 계산에 필요한 과거 구간(최소 약 52주)을 채우고, 이후에는 마지막 저장 거래일 이후의 누락분만 증분 수집한다. 이미 완전하게 저장된 거래일 데이터는 재요청하지 않는다.
4. 받은 데이터는 기준일·필드·정합성을 검사한 뒤 거래일과 종목 기준으로 upsert한다. 중복 실행에도 같은 데이터가 중복 저장되지 않게 한다. 보유량은 해당 일일 실행에서 한 번 조회하거나 사용자가 갱신한 값을 DB에서 읽는다.
5. 시장 일정에 따른 예상 최신 거래일과 일봉·수급·보유량의 기준 시각 및 누락 필드를 확인한다. 필수 데이터가 없거나 허용된 최신성 범위를 넘는 종목은 `데이터 확인 필요`로 보류하고 의견·수량을 만들지 않는다. 정상 종목은 DB 데이터와 새 데이터를 함께 사용해 이동평균, 52주 범위, 거래량 변화, 기관·외국인 순매수 지표를 계산한다.
6. 설정된 규칙으로 매수·매도·관망 의견을 만들고, 계좌 보유량과 매수 예산을 반영해 정수 주 단위 수량을 계산한다.
7. 종목별 의견·수량·근거·기준 거래일·누락 항목을 메시지에 넣는다. 모든 종목이 보류되어도 데이터 상태 브리핑을 발송한다.
8. 메시지 발신 어댑터로 카카오톡 발송을 시도하고, 성공·실패와 처리 결과를 SQLite에 기록한다.

데이터 수집·브리핑 발송과 수신 메시지 처리는 서로 다른 실행 흐름이다. 두 흐름은 같은 계좌·제안·데이터 품질 서비스를 호출한다. 메시지 수신은 상시 실행 API 컨테이너에서 처리한다.

```text
카카오톡 사용자 텍스트
    -> 카카오 수신 어댑터 (검증·공통 메시지로 변환)
    -> 공통 명령 처리기 (사용자 식별·파싱·권한 검사)
    -> 계좌/관심종목/제안/주문 서비스 -> SQLite·증권사 API
    -> 공통 텍스트 응답 -> 카카오 발신 어댑터 -> 카카오톡

다른 메신저 사용자 텍스트
    -> 해당 메신저 수신 어댑터 -> 동일한 공통 명령 처리기
    -> 공통 텍스트 응답 -> 해당 메신저 발신 어댑터

systemd timer (매일 08:30)
    -> Docker worker -> 공통 브리핑 서비스 -> 선택된 발신 어댑터
```

채널 어댑터는 메시지 수신·발신, 공급자가 제공하는 발신자 ID·대화 ID·메시지 ID를 공통 형식으로 변환하는 역할만 수행한다. 인증·파싱·대화 상태·업무 규칙·메시지 내용 구성은 공통 서비스가 담당한다. 플랫폼별 응답 시간·메시지 길이 제약은 어댑터 경계에서 처리하되 업무 결과를 바꾸지 않는다. 플랫폼이 임의 사용자 텍스트의 수신을 지원하는지, 08:30 발신 경로를 제공하는지는 구현 전 공식 기능으로 확인한다.

오전 8시 30분은 장 시작 전이므로 기본 분석 기준은 **전 거래일 종가와 전 거래일까지의 수급 데이터**로 한다. 휴장일에는 거래소 일정에 따른 마지막 거래일을 기준으로 삼는다. 필수 입력의 기준일이 예상 거래일보다 오래되거나 일부가 누락되면 해당 종목의 의견·수량을 보류한다. 기준일과 누락 사유는 반드시 표시한다.

## 3. 기능 설계

### 3.1 데이터 공급자 어댑터

증권사나 데이터 공급자를 교체할 수 있도록 공통 인터페이스와 공급자별 구현을 분리한다.

필요한 데이터 기능:

- 종목 코드·종목명 조회
- 기간별 일봉: 날짜, 시가, 고가, 저가, 종가, 거래량
- 기관과 외국인의 매수량·매도량 또는 순매수량
- 계좌 보유 종목과 보유 수량 (계좌 API 사용이 가능할 경우)
- API 요청 제한, 오류, 데이터 기준일 처리

초기에는 실제 주문 권한을 요청하지 않고, 조회 전용 키·권한이 가능하면 조회 전용으로 설정한다. 특정 API가 위 데이터 중 일부를 제공하지 않으면 지원 범위를 확인하고 별도 데이터 공급자 사용 여부를 결정한다.

권장 코드 경계:

```python
class BrokerProvider:
    def validate_credentials(self, credentials): ...
    def list_accounts(self): ...
    def get_holdings(self, account_id: str): ...

class MarketDataProvider:
    def get_daily_bars(self, symbol: str, start_date, end_date): ...
    def get_investor_flows(self, symbol: str, start_date, end_date): ...
```

한국투자증권용 `KisProvider`와 미래에셋증권용 `MiraeAssetProvider`를 같은 인터페이스로 구현한다. 각 provider의 인증 절차·계좌 조회·잔고 조회·시세/수급 범위는 실제 API 권한을 받은 뒤 확인해 매핑한다. 미래에셋을 포함한 각 증권사의 개인 개발자 API 접근 가능 여부와 이용 조건은 구현 착수 때 공식 창구에서 확인하며, 접근이 제공되지 않는 기능은 지원되는 데이터 공급자를 별도로 연결한다. 미지원 웹 화면을 긁거나 비공식 접근을 사용하지 않는다.

#### 증분 수집과 로컬 캐시

SQLite를 수집 데이터의 영속 캐시로 사용한다. 애플리케이션 코드는 `app/storage/sqlite_store.py`에서 DB 접근을 담당하고, 실제 DB 파일 `./stock-briefing.db`는 Ubuntu의 Docker 프로젝트 루트(`compose.yaml`과 같은 디렉터리)에 유지한다. Compose bind mount로 파일을 컨테이너에 연결한다. API 호출 전에 종목·데이터 종류별 저장 현황을 조회하고, 필요한 데이터가 이미 있으면 공급자 API를 호출하지 않는다.

- 최초 설정 때 관심 종목별로 52주 지표를 계산할 수 있는 과거 일봉과 필요한 수급 이력을 한 번 수집한다.
- 이후 정기 실행에서는 DB의 마지막 완전 거래일 이후 데이터만 요청한다. 거래일이 아닌 날에는 마지막 거래일 데이터가 완전하면 과거 구간을 다시 받지 않는다.
- 거래일과 종목을 고유 키로 두고 upsert해 재실행·응답 중복에도 행이 중복되지 않게 한다.
- 수급 자료도 종목·거래일·투자자 구분 기준으로 같은 방식으로 저장한다.
- 일부 종목 또는 데이터 종류의 응답이 빠졌다면 해당 누락 범위만 재요청한다. 이미 완료된 다른 종목·거래일은 다시 요청하지 않는다.
- 공급자가 과거 값을 정정할 수 있는 경우에만 최근 며칠 범위의 제한적인 재확인을 선택적으로 켠다. 기본 동작은 전체 재수집이 아니다.
- 보유량은 분석 실행당 한 번 조회해 스냅샷으로 저장한다. 계좌 조회 API가 없으면 직접 입력한 보유량을 DB에 저장하고 마지막 수정 시각을 표시한다.
- 수집 비용과 장애 분석을 위해 데이터 공급자, 기준 거래일, 수집 시각, 상태, 재시도 횟수를 `collection_state`에 기록한다.

이 설계로 52주 지표에 필요한 이력은 DB에서 계산하고, 매일의 API 요청은 새 거래일 데이터와 그날 필요한 보유량 조회로 제한한다.

### 3.2 지표 및 제안 규칙

각 종목에서 최소한 다음 값을 계산한다.

- 설정 기간별 이동평균선과 교차 상태
- 현재 종가의 최근 52주 최저가·최고가 대비 위치
- 당일 거래량과 최근 평균 거래량의 비율
- 기관 순매수량 및 외국인 순매수량과 최근 추이
- 데이터 기준일 및 입력 데이터의 완전성

규칙 엔진은 초기에는 설명 가능한 고정 규칙으로 구현한다. 기간, 임계값, 각 조건의 가중치와 최종 점수 구간은 아직 미정이므로 설정값으로 관리하고, 임의의 숫자를 기본값으로 확정하지 않는다.

각 제안에는 다음을 저장하고 메시지에 요약한다.

- 의견: 매수 / 매도 / 관망
- 제안 수량과 현재 보유 수량
- 판단에 사용한 지표 값과 규칙 요약
- 데이터 기준 거래일
- 제안이 보류된 경우 그 사유 (`데이터 확인 필요` 등)

#### 데이터 품질 판정

종목별 `daily_bars`와 `investor_flows`가 같은 예상 거래일까지 완전한지 확인하고, 계좌별 `holdings_snapshots`의 조회 시각도 확인한다. API 오류, 누락 필드, 거래일 불일치, 수집 지연은 각각 상태로 기록한다. 전략 설정에서 필수 지표·허용 데이터 지연 시간·수동 보유량의 허용 기준을 관리한다. 필수 데이터가 부족하면 매수·매도 의견과 제안 수량을 모두 생성하지 않고 `데이터 확인 필요`로 저장한다. 이전 제안을 최신 결과로 재사용하거나 주문 미리보기로 넘기지 않는다.

### 3.3 보유량 반영 수량 산정

수량 산정은 사용자가 설정한 예산·한도 안에서만 수행한다.

- 매수 수량은 종목별 최대 투자금과 남은 매수 예산을 넘지 않도록 계산한다.
- 매도 수량은 현재 보유량을 넘지 않도록 제한한다.
- 주식 수는 정수로 내림한다.
- 입력된 보유량을 확인할 수 없으면 매도 수량 제안을 만들지 않는다.
- 현금 잔고를 알 수 없으면 현금이 충분하다고 가정하지 않는다. 별도 설정 금액 또는 사용자가 입력한 예산이 없으면 매수 수량은 0주로 제시한다.
- 계산 결과가 0주이면 의견과 수량을 혼동하지 않도록 사유를 명시한다.

수량 산정 기준(종목별 비중, 최대 금액, 현금 한도, 최소 주문 단위)은 운영 전에 결정해야 한다.

### 3.4 카카오톡 브리핑

브리핑은 우선 사용자 본인의 카카오톡 **나와의 채팅방** 전송을 대상으로 설계한다.

메시지 예시 구조:

```text
[국내주식 아침 브리핑]
데이터 기준일: YYYY-MM-DD
데이터 상태: 정상 / 확인 필요 (누락 항목과 이유)

종목명 (종목코드)
의견: 매수 / 매도 / 관망
제안: N주 (현재 보유 N주)
근거: 이동평균선 · 52주 범위 · 거래량 · 기관/외국인 수급

...
```

- 데이터가 없거나 오래된 종목은 추천 대신 `데이터 확인 필요`, 기준 거래일, 누락 항목과 보류 사유를 보낸다.
- 추천 종목이 없을 때도 실행 성공 여부와 기준일을 알 수 있도록 짧은 브리핑을 보낸다.
- 카카오 로그인/동의 및 사용자 토큰 발급·갱신 절차를 사전 구현해야 한다.
- 친구에게 메시지를 보내는 기능은 1차 범위에 넣지 않는다. 친구 메시지는 별도 권한·수신자 선택 등 조건이 있으므로 필요해질 때 따로 검토한다.

### 3.5 메시지 명령과 채널 어댑터

카카오톡 수신·발신 구현은 `MessengerAdapter` 경계에 둔다. 수신 어댑터는 플랫폼 서명/토큰과 메시지 식별자를 검증하고 `InboundMessage(channel, sender_id, conversation_id, message_id, text, received_at)`로 바꾼다. 공통 명령 처리기는 메시지 ID 중복 여부 확인, 등록된 사용자 매핑, 텍스트 파싱과 입력값 검증을 거쳐 업무 서비스에 요청한다. 응답은 `OutboundMessage(destination, text)`로 만들고 선택된 채널 발신 어댑터가 전송한다. 어댑터에는 계좌 조회·매매 판단·주문 검증 로직을 두지 않는다.

초기 텍스트 명령의 예시는 아래와 같다. 실제 명령어와 도움말은 공통 명령 처리기 한 곳에서 정의한다. 해석되지 않는 입력은 지원 명령과 사용 예를 답한다.

| 메시지 예시 | 공통 서비스 동작 | 텍스트 응답 |
|---|---|---|
| `도움말` | 명령 목록 조회 | 가능한 요청과 입력 예시 |
| `증권사 연결 한국투자증권` | 등록 링크 발급 및 연결 검증 시작 | 일회용 HTTPS 링크와 후속 단계 |
| `연동 상태` | 연결·토큰·추적 계좌·데이터·발송 이력 조회 | 마스킹된 계좌, 기준 시각과 필요한 조치 |
| `추적 계좌 보기/추가/제거` | 계좌 목록·추적 상태 관리 | 마스킹 계좌와 처리 결과 |
| `관심종목 보기/추가/제거` | 관심종목 관리 | 종목명·코드와 처리 결과 |
| `보유종목` / `오늘 브리핑` | 추적 계좌·저장 제안 조회 | 보유량·의견·근거·데이터 기준일 |
| `브리핑 갱신` | 필요한 범위만 증분 수집 후 평가 | 처리 상태와 새 브리핑 |
| `설정 보기/변경` | 지표·예산·안전 한도·알림 관리 | 기존값·변경값·확인 안내 |
| `모의 운용 기록` | 사후 평가 이력 조회 | 평가 기준·적중률·가상 손익 |
| `주문 요청 ...` | 선택 계좌 주문 미리보기 생성 | 주문 요약·만료 시각·일회용 확인 코드 |
| `주문 확인 <코드>` | 공통 검증 후 선택 증권사 API 호출 | 접수 상태·주문 번호 또는 보류 사유 |
| `주문 정정/취소/상태 ...` | 증권사별 지원 범위 확인 | 처리 결과 또는 지원 불가 |
| `당일 주문 중지/재개` | 중지 상태 변경 및 감사 기록 | 적용 상태와 시각 |
| `서비스 상태` | 최근 작업·데이터·발송 상태 조회 | 상태와 필요한 조치 |

요청 처리 순서:

1. 수신 어댑터가 플랫폼 요청을 검증해 공통 메시지를 만들고, 동일 `channel + message_id`의 재전달을 중복 처리하지 않는다.
2. 공통 서비스가 `channel + sender_id`를 내부 사용자와 연결해 허용된 요청자인지 확인한다. 동일 사용자의 다른 채널 연결은 별도 등록·검증을 거친다. 텍스트를 명령으로 해석하고 계좌·종목·수량·가격을 검증한다. 임의 메시지를 코드나 셸 명령으로 실행하지 않는다.
3. 조회·관심종목·추적 계좌·설정 변경은 공통 서비스를 거쳐 SQLite transaction으로 처리하고 변경 이력을 남긴다. 설정 변경은 요약과 만료되는 일회용 확인 코드를 발급한다.
4. 주문 요청은 특정 사용자·채널·대화에 묶인 `pending_order`와 만료되는 일회용 확인 코드를 저장하고 주문 요약을 텍스트로 반환한다. 코드는 예측하기 어렵게 만들고 재사용을 막는다.
5. `주문 확인 <코드>`가 오면 동일 사용자·채널·대화인지, 코드가 유효하고 만료되지 않았는지, 동일한 요청인지 확인한다. 계좌의 잔고·보유량·금액 한도, 최신 가용 시세와 가격 이탈률, 당일 주문 중지 상태를 다시 검사한다. 실패 시 새 미리보기를 요청한다.
6. 실제 주문 기능이 비활성화되어 있으면 제출 불가로 응답한다. 활성화와 모든 검증을 통과한 경우에만 broker adapter에 요청한다.
7. 주문 요청 ID를 중복 방지 키로 기록한다. 이미 접수·체결된 주문과 진행 중 예약액을 합산하고, 전송 결과가 불명확하면 증권사 상태를 대조한 뒤에만 재시도한다.

발신·수신 실패와 비동기 처리 조건은 어댑터가 플랫폼별로 다룬다. 주문 결과와 계좌번호는 필요한 범위만 마스킹해 회신하며 비밀 키는 메시지 본문과 로그에 넣지 않는다.

### 3.6 연동 상태, 모의 운용 및 주문 안전 장치

- `연동 상태` 명령은 증권사별 연결/검증 결과, 토큰 만료 예정 시각과 갱신 오류(비밀값 제외), 추적 중인 마스킹 계좌, 필수 데이터의 마지막 완전 거래일, 최근 브리핑 작업과 카톡 발송 성공 여부를 한 화면에서 확인한다. 상태 조회 자체가 불필요한 시세 재수집을 일으키지 않도록 DB 기록을 우선 읽고, 사용자가 `브리핑 갱신`을 요청하면 필요한 범위만 조회한다.
- 모의 운용은 생성 당시의 제안, 추적 계좌, 기준 가격·거래일, 수량, 규칙 버전을 보존한다. 미리 설정한 평가 기간이 지난 뒤 실제 관측 가격을 저장하고 가상 매수·매도 및 청산 기준으로 손익을 계산한다. 수수료·세금·슬리피지는 적용 시점의 설정과 가정을 스냅샷으로 남기며 왕복 비용 여부를 명시한다. 적중률의 정의와 평가 기간을 함께 표시하고, 미평가/데이터 부족 사례는 분모에서 분리한다. 모의 결과를 실제 체결이나 확정 수익으로 표시하지 않는다.
- 주문 금액 한도는 추적 계좌별 종목 최대 금액과 하루 총 금액을 설정한다. 주문 요청 시와 최종 확인 시 모두 검증하며 진행 중인 주문의 예약 금액과 실제 접수·체결 금액을 중복 없이 합산한다. 가격 이탈 한도는 미리보기 기준 가격과 최종 확인 시의 최신 가용 시세를 비교한다. 시세가 없거나 오래되면 제출을 보류한다.
- `pending_orders`는 생성 시각·만료 시각·기준 가격·한도 검증 결과를 보관한다. 확인 유효 시간이 지났거나 가격 이탈 기준을 넘으면 무효화하고 새 미리보기를 요구한다. 당일 주문 중지는 선택한 거래일의 새로운 제출을 차단한다. 중지/재개를 일회용 확인 메시지로 확인받고 감사 기록에 남기며, 재개 후에도 만료된 요청은 다시 사용할 수 없다. 접수된 주문의 취소나 체결을 자동으로 소급 변경하지 않는다.
- 주문 기능은 기본적으로 꺼져 있다. 주문 중지 기능은 실제 주문 활성화 이후에 효력이 있고, 모의 운용 기록은 주문 기능이 꺼져 있을 때에도 제공한다.

### 3.7 증권사 API 연결과 추적 계좌

증권사 연결과 계좌 추적은 공통 텍스트 명령으로 시작한다. 계좌 선택과 보안정보 입력을 분리해 자격 증명을 일반 채팅 메시지로 남기지 않는다.

연결·추적 흐름:

1. 사용자가 `증권사 연결` 메시지에서 한국투자증권 또는 미래에셋증권을 고른다.
2. 서버는 짧은 만료 시간의 일회용 HTTPS 등록 링크를 발급한다. 사용자는 등록 화면에서 해당 증권사 API 키와 시크릿 등 필요한 인증정보를 입력한다.
3. 서버는 입력값을 로그·분석 도구에 기록하지 않고, 증권사 API에 연결 검증을 수행한다.
4. 검증이 끝나면 조회 가능한 계좌를 마스킹된 번호로 보여준다. 사용자는 추적할 계좌만 체크해 추가한다.
5. 선택한 계좌만 보유량 수집과 매매 제안 계산에 사용한다. 등록됐지만 추적하지 않는 계좌는 조회하지 않는다.
6. `추적 계좌` 메시지로 계좌를 추가·제거한다. 추적 제거는 이후 조회를 중단하되 기록 이력은 유지한다. `증권사 연결 해제`는 계좌 추적을 중단하고 해당 연결 자격 증명을 삭제한다.

API 키/시크릿은 SQLite에 평문 저장하지 않는다. `cryptography` 기반 인증된 암호화(AES-GCM 등)를 적용하고, 암호화 키는 Docker 프로젝트 폴더와 DB 파일 밖의 root 전용 파일 또는 Docker secret으로 전달한다. 카톡에는 등록 화면 링크만 보내며, 키/시크릿·전체 계좌번호를 채팅 메시지나 애플리케이션 로그에 남기지 않는다.

다중 계좌 지원은 이 서비스의 단일 사용자 범위 안에서만 제공한다. 계좌는 `broker + account_id` 식별자로 연결하고 사용자 표시에는 마스킹된 계좌번호를 쓴다. 추천·주문 요청은 반드시 특정 추적 계좌에 묶는다.

## 4. 구성 요소와 라이브러리

| 구성 요소 | 1차 선택 | 용도 |
|---|---|---|
| Python 런타임 | Python 3.13 계열 | Ubuntu Docker 컨테이너 실행 |
| HTTP API 서버 | `FastAPI`, `uvicorn` | 초기 카카오 수신 어댑터의 HTTPS 엔드포인트와 공통 명령 처리기 연결 |
| HTTP 클라이언트 | `httpx` | 증권·카카오 REST API 호출, timeout 설정 |

| 환경 설정 | `pydantic-settings` | 환경 변수와 설정값 로딩 및 검증 |

| 영속 저장 | Python 표준 `sqlite3` | 일일 실행, 데이터 기준일, 제안, 발송 상태 기록 |
| 시간대 | Python 표준 `zoneinfo` | Asia/Seoul 시간 해석 |
| 인증정보 암호화 | `cryptography` | 증권사 API 키/시크릿과 저장 토큰을 DB에 암호화 저장 |
| 테스트 | `pytest`, `respx` | 규칙·수량 계산과 HTTP API 응답 테스트 |
| 정적 검사 | `ruff` | lint와 포맷 일관성 |

단일 사용자·하루 한 번 분석 규모에 맞춰 Redis, Celery, PostgreSQL, 별도 기술적 분석 프레임워크는 기본 구성에 넣지 않는다. FastAPI는 초기 메시지 채널의 수신 요청을 받기 위해 사용하고, 별도 worker는 하루 한 번 실행한다. 지표 계산은 pandas로 직접 구현해 계산 근거와 결과를 검증할 수 있게 한다.

라이브러리의 정확한 패치 버전은 구현 시점에 확인해 lock 파일에 고정한다. Python 이미지는 패치 버전까지 고정하는 것을 배포 원칙으로 한다.

## 7. Ubuntu 및 Docker 운영

- `api` 서비스는 초기 카카오 메시지 수신 어댑터의 요청을 받는 FastAPI 컨테이너로 상시 실행한다. 다른 메신저 추가 시 해당 수신·발신 어댑터를 연결한다.
- `worker`는 데이터 수집·분석·브리핑 발송 후 종료하는 Docker one-shot 작업으로 구성한다. Ubuntu 호스트의 systemd timer가 매일 08:30에 `docker compose run --rm worker` 방식으로 실행한다.
- 초기 카카오 연동에 필요한 공개 HTTPS 주소를 준비하고, Caddy에서 수신 endpoint를 내부 API 컨테이너로 reverse proxy한다. 방화벽은 필요한 HTTPS 경로만 연다.
- API와 worker는 같은 영속 SQLite 파일을 사용한다. transaction, busy timeout, 백업을 설정하고, 하루 worker와 카톡 요청의 동시 쓰기가 안전하게 처리되는지 확인한다.
- 서버와 timer 기준 시간대를 Asia/Seoul로 맞추고, 앱 내부에서도 기준 시각을 명시적으로 기록한다.
- systemd timer의 missed-run 동작을 설정해 서버가 예약 시각에 꺼져 있던 경우의 처리 방침을 명확히 한다. 늦은 시각에 실행되면 오래된 데이터로 제안하지 않도록 데이터 기준일 검사를 한다.
- Compose의 `.env`는 Git에 커밋하지 않는다. 권한을 제한하고, 가능하면 Docker secrets 또는 root 전용 설정 파일을 사용한다.
- SQLite 파일은 **사용자가 만든 Docker 프로젝트 폴더 최상단**, 즉 `compose.yaml`과 같은 디렉터리의 `./stock-briefing.db`에 둔다. 하위 `data/` 폴더나 컨테이너 파일시스템에는 두지 않는다.
- Compose에서 `./stock-briefing.db`를 컨테이너의 `/app/data/stock-briefing.db`에 바인드 마운트하고 앱의 `SQLITE_PATH`도 이 컨테이너 경로로 지정한다. 파일이 없을 때 최초 실행에서 SQLite가 생성할 수 있도록 호스트 폴더 권한을 준비한다.
- `stock-briefing.db`와 SQLite WAL sidecar(`stock-briefing.db-wal`, `stock-briefing.db-shm`) 및 백업은 Git에서 제외한다. 배포 폴더가 저장소 clone 폴더와 같아도 실수로 커밋되지 않게 `.gitignore`에 등록한다.
- 컨테이너 내부 로그는 표준 출력으로 내보내고 Docker 로그 로테이션을 적용한다. DB 백업과 복원 절차는 Ubuntu 호스트에서 수행한다.
- 로그 로테이션, SQLite 백업, 백업 복원 절차를 설정한다.
- 네트워크/API 실패 시 제한 횟수로 재시도하고, 최종 실패는 로그로 남긴다. 재실행으로 같은 날짜의 제안·메시지가 중복 저장 또는 중복 전송되지 않도록 날짜별 실행 키를 둔다.

## 9. 검증 및 장애 처리

- 지표 계산: 작은 고정 일봉 데이터로 이동평균 교차·52주 최고/최저·거래량 비율을 검증한다.
- 수량 계산: 보유량 0, 예산 부족, 입력 보유량 누락, 매도 제안이 보유량을 초과할 수 있는 경계 조건을 검증한다.
- API: 정상 응답, 빈 응답, 지연, 429, 인증 만료, 잘못된 필드 응답을 모의 테스트한다.
- 브리핑: 휴장/전일 데이터 미갱신, 추천 없음, 일부 종목 데이터 실패 상황의 메시지를 확인한다.
- 중복 방지: 같은 거래일 작업을 재실행할 때 저장 결과와 발송 동작을 검증한다.
- 메시지 명령: 브리핑/보유량 조회, 관심종목 추가·삭제, 잘못된 종목코드·미지원 명령, 허용되지 않은 발신자, 재전달된 메시지를 테스트한다. 같은 명령을 다른 메신저 어댑터에서 전달해도 공통 서비스 결과가 동일한지 확인한다.
- 주문 확인: 일회용 확인 메시지 전에는 주문 API가 호출되지 않고, 만료된 요청·중복 클릭·금액 한도·가격 이탈·당일 중지·시세 누락이 차단되는지 테스트한다. 동시 확인 요청의 한도 예약과 접수 결과 불명확 시 상태 대조를 검증한다.
- 연동 상태: 토큰 만료·갱신 오류, 추적 계좌 표시, 마지막 완전 데이터 거래일과 최근 발송 실패 상태를 검증한다.
- 모의 운용: 제안 당시 기준 가격 보존, 평가 전/후 분리, 수수료·세금·슬리피지를 반영한 손익과 적중률 계산을 검증한다.
- 데이터 품질: 휴장일, 서로 다른 거래일의 일봉/수급, 일부 필드 누락과 오래된 보유량에서 해당 종목의 의견·수량이 보류되는지 검증한다.
- 운영 전에는 모의 데이터·모의 API로 실행 결과를 확인하고, 주문 기능 비활성 설정에서 주문 API가 호출되지 않는 것을 점검한다.

## 10. 메시지 기반 전체 기능 사용 원칙

- 모든 사용자 기능은 일반 텍스트 메시지로 요청하고 결과를 텍스트로 받는다. 도움말·입력 예시와 다단계 확인 문구는 공통 서비스에서 관리한다.
- 카카오 연동 코드는 메시지 수신·발신과 공통 형식 변환에만 관여한다. 계좌·관심종목·분석 설정·데이터·브리핑·주문 로직은 채널 독립 서비스에 둔다.
- 새 메신저를 연결할 때에는 해당 채널 어댑터와 사용자 ID 연결·검증 절차를 추가한다. 같은 공통 명령과 업무 규칙을 재사용한다. 이후 대시보드를 만든다면 같은 서비스 경계를 사용할 수 있다.
- 증권사 키/시크릿은 공통 서비스가 발급한 짧은 만료 HTTPS 링크에서 입력한다. 비밀 값을 메시지나 로그에 남기지 않는다.
- 설정 변경과 주문 실행은 변경 전 요약과 유효 시간이 짧은 일회용 확인 코드가 포함된 메시지로 확인한다. 확인 코드는 사용자·채널·대화·요청과 묶고 한 번만 사용한다.
- 정기 브리핑은 08:30 공통 서비스가 생성하고 설정된 채널 발신 어댑터가 전달한다. 재조회는 DB를 사용하고 재수집은 누락분만 요청한다.

## 11. 구현 전 결정할 사항

1. 한국투자증권과 미래에셋증권 각각의 개발자 API 신청·사용 가능 여부, 인증, 계좌 목록·잔고·시세·수급 지원 범위와 호출 한도 확인
2. API 키·시크릿 등록 화면의 배포 주소, 인증/암호화 키 보관과 회전 방법 결정
3. 추적할 계좌를 선택·추가·제거하는 흐름과 계좌 연결 해제 시 보존할 이력 범위 결정
4. 종목 목록을 고정 관심종목으로 둘지, 추적 계좌 보유 종목에서 자동 구성할지
5. 카카오 공식 채널에서 임의 텍스트 메시지 수신과 매일 08:30 발신을 각각 지원하는지, 필요한 이용 동의·토큰 갱신과 운영 조건 확인
6. 이동평균 기간, 지표 임계값, 의견 점수와 관망 구간
7. 매수 예산, 종목별 최대 투자금, 매도 수량·잔량 처리 정책
8. 데이터가 지연되거나 서버가 08:30에 꺼져 있을 때 늦은 브리핑을 보낼지 여부
9. 메신저 토큰과 계좌 데이터의 저장·백업·암호화 방식
10. 모의 평가 기간·가격 기준 및 수수료·세금·슬리피지 가정, 적중률 산식
11. 거래일별 데이터 허용 지연·필수 필드, 보유량 스냅샷 허용 시간
12. 계좌·종목별 및 일별 주문 한도, 가격 이탈률과 확인 유효 시간
