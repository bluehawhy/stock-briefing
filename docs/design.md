# 국내주식 매매 제안 브리핑 서비스 설계서

- 문서 상태: 초안
- 대상 저장소: `bluehawhy/stock-briefing`
- 구현 언어: Python
- 운영 환경: 집의 Ubuntu 서버 + Docker
- 실행 주기: 매일 오전 8시 30분 (Asia/Seoul)

## 1. 목표와 범위

국내 주식의 전 거래일 데이터와 현재 보유 수량을 바탕으로 종목별 매수·매도·관망 의견과 제안 수량을 계산하고, 매일 오전 8시 30분 카카오톡으로 요약을 전달한다. 카카오톡에는 고정 메뉴와 버튼을 제공해 사용자가 브리핑·보유량·관심종목을 조회하고 관심종목을 추가·삭제하도록 한다. 서버는 버튼 요청을 받아 DB/API 작업을 수행하고 결과를 카톡으로 응답한다.

### 1차 버전에서 할 일

- 국내 주식 시세, 일봉, 거래량, 기관·외국인 수급 데이터 조회
- 이동평균선 교차, 52주 가격 범위, 거래량, 투자자별 순매수 조건 계산
- 보유량과 설정된 예산 한도를 고려한 매매 제안 수량 산정
- 제안 근거를 포함한 카카오톡 브리핑 발송
- 카카오톡 고정 메뉴/버튼을 통한 브리핑·보유량·관심종목 조회와 관심종목 추가·삭제
- 카카오 챗봇 스킬 요청을 Ubuntu Python 서버가 받아 DB/API 작업을 수행하고 카톡으로 결과 응답
- 주문 요청 시 주문 요약을 보여주고 사용자 확인을 받는 대화 흐름
- 실행 결과, 데이터 기준일, 추천 결과, 발송 상태 기록
- 상시 대기하는 챗봇 API 컨테이너와 매일 한 번 실행되는 Docker 작업 컨테이너 운영

### 1차 버전에서 제외할 일

- 확인 버튼을 누르지 않은 주문의 자동 제출
- 여러 사용자·여러 계좌를 위한 서비스
- 실시간 시세 감시, 웹 대시보드, 모델 학습 기반 예측

실제 주문 제출은 1차 기본 설정에서 비활성화한다. 선택한 증권사 API의 주문 기능·계좌 설정을 확인하고, 명시적으로 활성화한 뒤에도 주문 요약과 별도 확인을 거쳐야 제출한다. 제안 생성만으로 주문하지 않는다.

## 2. 제안 흐름

```text
Ubuntu systemd timer (매일 08:30 KST)
        |
        v
Docker Compose one-shot 실행
        |
        v
설정·최근 실행 확인
        |
        v
시장 데이터 + 보유량 조회
        |
        v
데이터 최신성·정합성 검사
        |
        v
지표 계산 -> 규칙 평가 -> 수량 산정
        |
        v
브리핑 생성 -> 카카오톡 발송
        |
        v
SQLite 실행 기록·발송 결과 저장
```

### 단계별 동작

1. 서버의 systemd timer가 매일 08:30에 Docker Compose 작업 컨테이너를 실행한다.
2. SQLite에서 종목별 일봉·수급 데이터의 저장 범위와 마지막 완전 수집 거래일을 확인한다.
3. 아직 없는 거래일 데이터만 데이터 공급자 어댑터로 요청한다. 최초 실행 때만 지표 계산에 필요한 과거 구간(최소 약 52주)을 채우고, 이후에는 마지막 저장 거래일 이후의 누락분만 증분 수집한다. 이미 완전하게 저장된 거래일 데이터는 재요청하지 않는다.
4. 받은 데이터는 기준일·필드·정합성을 검사한 뒤 거래일과 종목 기준으로 upsert한다. 중복 실행에도 같은 데이터가 중복 저장되지 않게 한다. 보유량은 해당 일일 실행에서 한 번 조회하거나 사용자가 갱신한 값을 DB에서 읽는다.
5. 저장된 DB 데이터와 새로 수집한 데이터를 함께 사용해 이동평균, 52주 범위, 거래량 변화, 기관·외국인 순매수 지표를 계산한다.
6. 설정된 규칙으로 매수·매도·관망 의견을 만들고, 계좌 보유량과 매수 예산을 반영해 정수 주 단위 수량을 계산한다.
7. 종목별 의견·수량·근거·데이터 기준일이 들어간 메시지를 만든다.
8. 카카오톡 발송을 시도하고, 성공·실패와 처리 결과를 SQLite에 기록한다.

데이터 수집·브리핑 발송과 카카오톡 메뉴 요청은 서로 다른 실행 흐름이다. 메뉴 요청은 상시 실행 API 컨테이너가 처리한다.

```text
사용자 고정 메뉴/버튼
        |
        v
카카오톡 채널 챗봇 (Open Builder Skill)
        |
        v
공개 HTTPS 스킬 엔드포인트 (집 Ubuntu / Caddy)
        |
        v
Python 명령 처리 -> 권한 확인 -> SQLite/증권사 조회
        |
        v
정의된 응답을 카카오톡에 반환

systemd timer (매일 08:30) -> Docker one-shot worker -> 브리핑 발송
```

오전 8시 30분은 장 시작 전이므로 기본 분석 기준은 **전 거래일 종가와 전 거래일까지의 수급 데이터**로 한다. 당일 데이터가 제공되지 않거나 기준일이 예상보다 오래되면 그 사실을 메시지에 표시하거나 제안을 중단한다.

## 3. 기능 설계

### 3.1 데이터 공급자 어댑터

증권사나 데이터 공급자를 교체할 수 있도록 공통 인터페이스와 공급자별 구현을 분리한다.

필요한 데이터 기능:

- 종목 코드·종목명 조회
- 기간별 일봉: 날짜, 시가, 고가, 저가, 종가, 거래량
- 기관과 외국인의 매수량·매도량 또는 순매수량
- 계좌 보유 종목과 보유 수량 (계좌 API 사용이 가능할 경우)
- API 요청 제한, 오류, 데이터 기준일 처리

초기에는 실제 주문 권한을 요청하지 않고, 조회 전용 키·권한이 가능하면 조회 전용으로 설정한다. 특정 API가 위 데이터 중 일부를 제공하지 않으면 지원 범위를 확인하고 별도 데이터 공급자 사용 여부를 결정한다.

권장 코드 경계:

```python
class MarketDataProvider:
    def get_daily_bars(self, symbol: str, start_date, end_date): ...
    def get_investor_flows(self, symbol: str, start_date, end_date): ...
    def get_holdings(self): ...
```

인터페이스는 실제 공급자 API의 응답 필드·호출 한도·인증 방식 확인 뒤 구체화한다.

#### 증분 수집과 로컬 캐시

SQLite를 수집 데이터의 영속 캐시로 사용한다. 애플리케이션 코드는 `app/storage/sqlite_store.py`에서 DB 접근을 담당하고, 실제 DB 파일 `./stock-briefing.db`는 Ubuntu의 Docker 프로젝트 루트(`compose.yaml`과 같은 디렉터리)에 유지한다. Compose bind mount로 파일을 컨테이너에 연결한다. API 호출 전에 종목·데이터 종류별 저장 현황을 조회하고, 필요한 데이터가 이미 있으면 공급자 API를 호출하지 않는다.

- 최초 설정 때 관심 종목별로 52주 지표를 계산할 수 있는 과거 일봉과 필요한 수급 이력을 한 번 수집한다.
- 이후 정기 실행에서는 DB의 마지막 완전 거래일 이후 데이터만 요청한다. 거래일이 아닌 날에는 마지막 거래일 데이터가 완전하면 과거 구간을 다시 받지 않는다.
- 거래일과 종목을 고유 키로 두고 upsert해 재실행·응답 중복에도 행이 중복되지 않게 한다.
- 수급 자료도 종목·거래일·투자자 구분 기준으로 같은 방식으로 저장한다.
- 일부 종목 또는 데이터 종류의 응답이 빠졌다면 해당 누락 범위만 재요청한다. 이미 완료된 다른 종목·거래일은 다시 요청하지 않는다.
- 공급자가 과거 값을 정정할 수 있는 경우에만 최근 며칠 범위의 제한적인 재확인을 선택적으로 켠다. 기본 동작은 전체 재수집이 아니다.
- 보유량은 분석 실행당 한 번 조회해 스냅샷으로 저장한다. 계좌 조회 API가 없으면 직접 입력한 보유량을 DB에 저장하고 마지막 수정 시각을 표시한다.
- 수집 비용과 장애 분석을 위해 데이터 공급자, 기준 거래일, 수집 시각, 상태, 재시도 횟수를 `collection_state`에 기록한다.

이 설계로 52주 지표에 필요한 이력은 DB에서 계산하고, 매일의 API 요청은 새 거래일 데이터와 그날 필요한 보유량 조회로 제한한다.

### 3.2 지표 및 제안 규칙

각 종목에서 최소한 다음 값을 계산한다.

- 설정 기간별 이동평균선과 교차 상태
- 현재 종가의 최근 52주 최저가·최고가 대비 위치
- 당일 거래량과 최근 평균 거래량의 비율
- 기관 순매수량 및 외국인 순매수량과 최근 추이
- 데이터 기준일 및 입력 데이터의 완전성

규칙 엔진은 초기에는 설명 가능한 고정 규칙으로 구현한다. 기간, 임계값, 각 조건의 가중치와 최종 점수 구간은 아직 미정이므로 설정값으로 관리하고, 임의의 숫자를 기본값으로 확정하지 않는다.

각 제안에는 다음을 저장하고 메시지에 요약한다.

- 의견: 매수 / 매도 / 관망
- 제안 수량과 현재 보유 수량
- 판단에 사용한 지표 값과 규칙 요약
- 데이터 기준 거래일
- 제안이 보류된 경우 그 사유

### 3.3 보유량 반영 수량 산정

수량 산정은 사용자가 설정한 예산·한도 안에서만 수행한다.

- 매수 수량은 종목별 최대 투자금과 남은 매수 예산을 넘지 않도록 계산한다.
- 매도 수량은 현재 보유량을 넘지 않도록 제한한다.
- 주식 수는 정수로 내림한다.
- 입력된 보유량을 확인할 수 없으면 매도 수량 제안을 만들지 않는다.
- 현금 잔고를 알 수 없으면 현금이 충분하다고 가정하지 않는다. 별도 설정 금액 또는 사용자가 입력한 예산이 없으면 매수 수량은 0주로 제시한다.
- 계산 결과가 0주이면 의견과 수량을 혼동하지 않도록 사유를 명시한다.

수량 산정 기준(종목별 비중, 최대 금액, 현금 한도, 최소 주문 단위)은 운영 전에 결정해야 한다.

### 3.4 카카오톡 브리핑

브리핑은 우선 사용자 본인의 카카오톡 **나와의 채팅방** 전송을 대상으로 설계한다.

메시지 예시 구조:

```text
[국내주식 아침 브리핑]
데이터 기준일: YYYY-MM-DD

종목명 (종목코드)
의견: 매수 / 매도 / 관망
제안: N주 (현재 보유 N주)
근거: 이동평균선 · 52주 범위 · 거래량 · 기관/외국인 수급

...
```

- 데이터가 없거나 오래된 종목은 추천 대신 데이터 상태와 보류 사유를 보낸다.
- 추천 종목이 없을 때도 실행 성공 여부와 기준일을 알 수 있도록 짧은 브리핑을 보낸다.
- 카카오 로그인/동의 및 사용자 토큰 발급·갱신 절차를 사전 구현해야 한다.
- 친구에게 메시지를 보내는 기능은 1차 범위에 넣지 않는다. 친구 메시지는 별도 권한·수신자 선택 등 조건이 있으므로 필요해질 때 따로 검토한다.

### 3.5 고정 메뉴와 챗봇 명령 처리

자유 형식 메시지를 임의 코드나 명령으로 실행하지 않는다. 카카오 챗봇에 등록한 고정 블록·버튼·선택 메뉴만 서버 동작에 연결한다. 각 버튼은 서버가 식별할 수 있는 명령 종류와 검증된 파라미터를 전달한다.

초기 명령 세트:

| 카카오 메뉴/버튼 | 서버 동작 | 응답 |
|---|---|---|
| 오늘 브리핑 | 최신 추천·기준일 DB 조회 | 종목별 의견·수량·근거 |
| 관심종목 보기 | 관심종목 테이블 조회 | 종목명·코드 목록 |
| 관심종목 추가 | 종목코드 검증 후 DB 저장 | 추가 결과 |
| 관심종목 제거 | 해당 종목 DB에서 제거 | 제거 결과 |
| 보유종목 보기 | 최신 holdings snapshot 조회 | 종목별 보유 수량·기준 시각 |
| 매수/매도 제안 확인 | 저장된 추천 조회 | 방향·수량·근거 |
| 주문 요청 | 주문 요약 생성, 아직 주문하지 않음 | 종목·방향·수량·가격 확인 버튼 |
| 주문 확인/취소 | 확인 요청 검증 후 주문 실행 또는 취소 | 처리 결과·주문 번호 |

요청 처리 순서:

1. 카카오 챗봇의 스킬 요청에서 고정 명령과 파라미터를 읽는다.
2. 허용된 카카오 사용자 ID인지 확인하고, 종목 코드·수량·가격 등 입력을 검증한다.
3. 조회·관심종목 변경은 SQLite transaction으로 처리한다.
4. 주문 요청은 짧은 만료 시간을 가진 `pending_order`로 저장하고 주문 요약을 반환한다.
5. 사용자가 주문 확인 버튼을 누르면 미리 저장한 요청과 동일한 주문인지, 만료되지 않았는지, 잔고·수량 한도를 넘지 않는지 확인한다.
6. 실제 주문 기능이 비활성화되어 있으면 주문을 제출하지 않고 비활성 상태를 응답한다. 활성화되어 있고 모든 검증을 통과한 경우에만 broker adapter에 주문 요청을 전달한다.
7. 주문 요청 ID를 idempotency key로 기록해 같은 확인 버튼의 반복 전달이 중복 주문이 되지 않도록 한다.

카카오 스킬 서버는 외부에서 접속 가능한 HTTPS endpoint로 운영한다. 메뉴 응답은 짧은 시간 내 반환해야 하므로 계좌/시장 API를 호출하는 명령은 timeout과 오류 응답을 설정하고, 긴 처리는 비동기 callback 기능이 허용되는지 확인한다. 비밀 키와 계좌 정보는 카카오 요청/응답 본문에 넣지 않는다.

## 4. 구성 요소와 라이브러리

| 구성 요소 | 1차 선택 | 용도 |
|---|---|---|
| Python 런타임 | Python 3.13 계열 | Ubuntu Docker 컨테이너 실행 |
| HTTP API 서버 | `FastAPI`, `uvicorn` | 카카오 챗봇 스킬 요청을 받을 HTTPS 웹훅 엔드포인트 |
| HTTP 클라이언트 | `httpx` | 증권·카카오 REST API 호출, timeout 설정 |
| 데이터 처리 | `pandas` | 일봉 정렬, 이동평균·rolling 52주 고저·거래량 통계 |
| 환경 설정 | `pydantic-settings` | 환경 변수와 설정값 로딩 및 검증 |
| 재시도 | `tenacity` | 일시적 네트워크 오류 재시도. 인증·권한·요청값 오류는 재시도하지 않음 |
| 영속 저장 | Python 표준 `sqlite3` | 일일 실행, 데이터 기준일, 제안, 발송 상태 기록 |
| 시간대 | Python 표준 `zoneinfo` | Asia/Seoul 시간 해석 |
| 시크릿 암호화 | `cryptography` (필요 시) | SQLite에 토큰을 저장해야 할 경우 보호 |
| 테스트 | `pytest`, `respx` | 규칙·수량 계산과 HTTP API 응답 테스트 |
| 정적 검사 | `ruff` | lint와 포맷 일관성 |

단일 사용자·하루 한 번 분석 규모에 맞춰 Redis, Celery, PostgreSQL, 별도 기술적 분석 프레임워크는 기본 구성에 넣지 않는다. FastAPI는 카카오 챗봇의 고정 메뉴 요청을 받기 위해 사용하고, 별도 worker는 하루 한 번 실행한다. 지표 계산은 pandas로 직접 구현해 계산 근거와 결과를 검증할 수 있게 한다.

라이브러리의 정확한 패치 버전은 구현 시점에 확인해 lock 파일에 고정한다. Python 이미지는 패치 버전까지 고정하는 것을 배포 원칙으로 한다.

`daily_bars`에는 `(provider, symbol, trade_date)`, `investor_flows`에는 `(provider, symbol, trade_date, investor_type)` 고유 제약을 둬 중복 수집을 방지한다. 마지막 기준일 이후의 결측 범위만 조회하는 쿼리를 제공하고, 52주 지표는 저장된 거래일 이력에서 계산한다.

토큰, API 키, 개인 계좌 정보는 로그에 출력하지 않는다. 데이터베이스 파일과 백업 파일은 Git에 올리지 않는다.

## 7. Ubuntu 및 Docker 운영

- `api` 서비스는 카카오 챗봇 스킬 요청을 받는 FastAPI 컨테이너로 상시 실행한다.
- `worker`는 데이터 수집·분석·브리핑 발송 후 종료하는 Docker one-shot 작업으로 구성한다. Ubuntu 호스트의 systemd timer가 매일 08:30에 `docker compose run --rm worker` 방식으로 실행한다.
- 카카오 챗봇이 접근할 공개 HTTPS 주소를 준비하고, Caddy에서 스킬 endpoint를 내부 API 컨테이너로 reverse proxy한다. 방화벽은 필요한 HTTPS 경로만 연다.
- API와 worker는 같은 영속 SQLite 파일을 사용한다. transaction, busy timeout, 백업을 설정하고, 하루 worker와 카톡 요청의 동시 쓰기가 안전하게 처리되는지 확인한다.
- 서버와 timer 기준 시간대를 Asia/Seoul로 맞추고, 앱 내부에서도 기준 시각을 명시적으로 기록한다.
- systemd timer의 missed-run 동작을 설정해 서버가 예약 시각에 꺼져 있던 경우의 처리 방침을 명확히 한다. 늦은 시각에 실행되면 오래된 데이터로 제안하지 않도록 데이터 기준일 검사를 한다.
- Compose의 `.env`는 Git에 커밋하지 않는다. 권한을 제한하고, 가능하면 Docker secrets 또는 root 전용 설정 파일을 사용한다.
- SQLite 파일은 **사용자가 만든 Docker 프로젝트 폴더 최상단**, 즉 `compose.yaml`과 같은 디렉터리의 `./stock-briefing.db`에 둔다. 하위 `data/` 폴더나 컨테이너 파일시스템에는 두지 않는다.
- Compose에서 `./stock-briefing.db`를 컨테이너의 `/app/data/stock-briefing.db`에 바인드 마운트하고 앱의 `SQLITE_PATH`도 이 컨테이너 경로로 지정한다. 파일이 없을 때 최초 실행에서 SQLite가 생성할 수 있도록 호스트 폴더 권한을 준비한다.
- `stock-briefing.db`와 SQLite WAL sidecar(`stock-briefing.db-wal`, `stock-briefing.db-shm`) 및 백업은 Git에서 제외한다. 배포 폴더가 저장소 clone 폴더와 같아도 실수로 커밋되지 않게 `.gitignore`에 등록한다.
- 컨테이너 내부 로그는 표준 출력으로 내보내고 Docker 로그 로테이션을 적용한다. DB 백업과 복원 절차는 Ubuntu 호스트에서 수행한다.
- 로그 로테이션, SQLite 백업, 백업 복원 절차를 설정한다.
- 네트워크/API 실패 시 제한 횟수로 재시도하고, 최종 실패는 로그로 남긴다. 재실행으로 같은 날짜의 제안·메시지가 중복 저장 또는 중복 전송되지 않도록 날짜별 실행 키를 둔다.

## 8. 설정값 초안

`.env.example`에 변수 이름과 설명만 제공하고 실제 값은 저장하지 않는다.

- `APP_TIMEZONE=Asia/Seoul`
- `BRIEFING_TIME=08:30`
- `DATA_PROVIDER=`
- 증권 데이터 API의 실전/모의 URL 구분 설정
- 종목 코드 목록
- 이동평균 기간, 거래량 비교 기간 등 전략 파라미터
- 종목별 투자 상한 및 매수 예산
- 카카오 REST API 설정과 OAuth 토큰 파일/저장 경로
- SQLite 경로와 로그 수준
- 카카오 Open Builder 스킬 endpoint와 허용된 카카오 사용자 ID 목록
- 주문 기능 활성화 여부(기본값 false), 주문 한도, 확인 유효 시간
- 최초 이력 수집 기간, 거래일별 수집 상태, 선택적 최근 데이터 재검증 범위

비밀 값은 예시 파일에 넣지 않는다. 모의 API와 실전 API 설정을 분리해 실수로 실전 주문 권한을 사용하지 않도록 한다. 1차 앱은 주문 API를 호출하지 않는다.

## 9. 검증 및 장애 처리

- 지표 계산: 작은 고정 일봉 데이터로 이동평균 교차·52주 최고/최저·거래량 비율을 검증한다.
- 수량 계산: 보유량 0, 예산 부족, 입력 보유량 누락, 매도 제안이 보유량을 초과할 수 있는 경계 조건을 검증한다.
- API: 정상 응답, 빈 응답, 지연, 429, 인증 만료, 잘못된 필드 응답을 모의 테스트한다.
- 브리핑: 휴장/전일 데이터 미갱신, 추천 없음, 일부 종목 데이터 실패 상황의 메시지를 확인한다.
- 중복 방지: 같은 거래일 작업을 재실행할 때 저장 결과와 발송 동작을 검증한다.
- 고정 메뉴 요청: 브리핑/보유량 조회, 관심종목 추가·삭제, 잘못된 종목코드, 허용되지 않은 카카오 사용자 요청을 테스트한다.
- 주문 확인: 확인 전에는 주문 API가 호출되지 않고, 만료된 요청·중복 클릭·수량 한도 초과가 차단되는지 테스트한다.
- 운영 전에는 모의 데이터·모의 API로 실행 결과를 확인하고, 주문 기능 비활성 설정에서 주문 API가 호출되지 않는 것을 점검한다.

## 10. 구현 전 결정할 사항

1. 최종 시장 데이터 API 및 증권사: 시세·일봉·수급·보유량 제공 범위, 인증, 호출 한도 확인
2. 종목 목록을 고정 관심종목으로 둘지, 계좌 보유 종목에서 자동 구성할지
3. Kakao Developers에서 본인 나와의 채팅 메시지 API 이용 동의와 토큰 갱신을 구성할 수 있는지 확인
4. 이동평균 기간, 지표 임계값, 의견 점수와 관망 구간
5. 매수 예산, 종목별 최대 투자금, 매도 수량·잔량 처리 정책
6. 데이터가 지연되거나 서버가 08:30에 꺼져 있을 때 늦은 브리핑을 보낼지 여부
7. 카카오 토큰과 계좌 데이터의 저장·백업·암호화 방식
